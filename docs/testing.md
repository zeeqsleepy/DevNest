# Testing Strategy

Status: current as of Phase 10
Last revised: 2026-07-24

Tests exist so that changing this codebase in a year is not frightening. That goal drives every
decision below. In particular, tests must be fast enough to run constantly and reliable enough
that a red result always means something.

## Layers

```
                        ┌──────────────┐
                        │  end-to-end  │  a few dozen, the built binary,
                        │              │  real filesystem, per platform
                     ┌──┴──────────────┴──┐
                     │    integration     │  a few hundred, real platform
                     │                    │  layer, real temp directories
                  ┌──┴────────────────────┴──┐
                  │        unit               │  the great majority, modules
                  │                           │  against fakes, no real I/O
                  └───────────────────────────┘
```

The shape is conventional because it works: most defects are caught in the layer that is fastest
to run and easiest to debug.

## Unit tests

**Where.** Beside the code, in the same package. `scan.go` is tested by `scan_test.go`.

**What.** A module's entry function, called with a `Request`, asserting on the returned `Result`.
Because modules are functions from data to data, this needs no setup beyond constructing a struct.

**Isolation.** No real filesystem, no real network, no real process table. Dependencies arrive
through the narrow interfaces declared in the module's `deps.go`, and tests supply fakes:

- A fake filesystem holding an in-memory tree, able to return permission errors, symlink loops,
  and unreadable files on demand.
- A fake process lister returning a fixed table.
- A fake HTTP round-tripper returning canned responses.
- A fake clock, so anything time-dependent is deterministic.

The payoff is not purity. It is that a test for "scan handles a permission error mid-walk" needs
no elevated test runner, no platform-specific setup, and no cleanup, and it runs on every
platform identically.

**Style.** Table-driven wherever there is more than a case or two:

```go
tests := []struct {
    name    string
    input   Request
    want    Result
    wantErr errors.Code
}{ ... }
```

Subtests via `t.Run` so a failure names the case. Struct literals use field names, always:
positional literals break silently when a field is added.

**Speed.** The unit suite completes in under 10 seconds on a developer machine. It is expected to
be run on every save; anything slower stops being run.

## The platform layer's own tests

**Where.** Beside the code, in `internal/platform/*`, and **not** behind a build tag.

**Why not tagged.** This layer is the seam to the outside world. A test of a tree walker, a
rename, or a case-insensitive path comparison that runs against a fake proves only that the fake
agrees with itself. Tagging these would keep the most safety-critical code in the project out of
`make test`, which is exactly backwards.

They use `t.TempDir()`, so they clean up after themselves and depend on nothing about the machine
running them. That is what makes running them by default reasonable, and it is the condition R35
attaches to the exception.

**What.** Walking with depth limits, exclusions, hidden files, symlink cycles, and cancellation;
moving with the refusal to replace; containment and path identity under each platform's case
rules; digests against published values; the protected-path table.

## Integration tests

**Where.** `tests/`, behind the `integration` build tag.

**What.** Whole operations end to end on a real tree (organise, rename, duplicates, filter, size,
hash) plus the guards that only mean something against a real filesystem, such as the refusal to
run in a home directory. This is the join between the module and the platform layer, which neither
one's own tests exercise.

Still to come, as the modules that need them arrive:

- `platform/proc` against a real child process started by the test itself.
- `platform/net` against a listener the test opened, so "port in use" is a fact rather than a
  fixture.

**Fixtures.** `fixtures/` holds constructed miniature projects: a Node project with
`node_modules`, a Go project with build output, a repository with planted fake credentials. Large
ones are generated by a script rather than committed, so the repository stays small.

**Cleanup.** `t.TempDir()` for everything, so cleanup is automatic even when a test fails. No test
ever writes outside its temporary directory, and a test that does is a bug regardless of whether
it passes.

## End-to-end tests

**Where.** `tests/`, tagged separately again.

**What.** The built binary, executed as a subprocess, with real arguments and real streams.
Verifies the things only a real process can verify:

- Exit codes for every documented code.
- stdout contains only results; stderr contains only logs. Asserted at every verbosity level,
  because this is the contract that makes piping work and it is easy to break by accident.
- JSON output parses and matches the expected schema.
- `--help` works for every command, and every command has a description and at least two examples.
- Signal handling: send an interrupt mid-run, expect exit 5 and a clean unwind.
- Destructive commands do nothing without `--apply`: asserted by checking the tree afterwards,
  not by reading the output.

**Cost.** Slow, so kept few and reserved for contracts rather than behaviour. Behaviour is a unit
test's job.

## Cross-platform testing

CI runs the full suite on Windows, Linux, and macOS for every push. Windows is not an optional job
that gets disabled when it goes red.

Platform-specific code under `internal/platform` gets platform-specific tests via build tags. Each
platform's socket enumeration, process listing, path handling, and permission model is tested on
that platform. A test that cannot pass on a platform is skipped explicitly with a documented
reason and a linked issue, never left silently failing.

Windows-specific cases that get their own tests because they are where cross-platform code
usually breaks: paths over 260 characters, UNC paths, drive-relative paths, junctions and reparse
points, files locked by another process, and case-insensitive but case-preserving path
comparison.

## Benchmarks

**Where.** `benchmarks/`, separate from unit tests because they are slow and need a quiet machine
to mean anything.

**What.** The operations whose performance targets are stated in `performance.md`: cold startup,
a scan of a 10,000-file tree, hashing a 1 GB file, socket enumeration, secret scanning.

**Baselines.** Committed alongside the benchmark code, annotated with the hardware they were
measured on. A comparison script reports drift.

**In CI.** Benchmarks run on a schedule, not on every push: shared runners are too noisy for the
numbers to be trustworthy per-commit. A regression beyond the threshold in `performance.md` opens
an issue rather than failing a build, because a noisy benchmark failing a build teaches people to
ignore it.

## Test data

- **`testdata/`** at the root: fixtures shared across packages, malformed JSON and YAML, captured
  toolchain version output, captured platform socket output, expected rendering output.
- **`<package>/testdata/`**: fixtures used by one package only. Most fixtures belong here.
- **`fixtures/`**: whole constructed project trees for scenario tests.

Go excludes any directory named `testdata` from the build, which is why the name is fixed.

Every fixture has a comment or a `README` saying where it came from and what it is for. An
unexplained fixture cannot be updated safely by anyone who did not add it.

## Rules

**Determinism.** No dependence on map iteration order, wall-clock time, hostname, locale, or
environment. Seeded randomness is acceptable; unseeded is not.

**No sleeping.** Time is injected. Waiting is done with synchronisation. `time.Sleep` in a test is
a flake with a delay attached.

**No network.** Unit and integration tests never make an outbound connection. HTTP behaviour is
tested against a local `httptest` server or a fake round-tripper.

**No shared state.** Tests run in parallel where possible and must not depend on execution order.
`t.Parallel()` wherever the test permits it.

**Assert on codes, not messages.** Error assertions compare `errors.Code`. Message wording
improves; codes do not.

**Race detector always.** `-race` on every CI run. A data race is a defect even when the test
passes.

**Coverage floors: 80% on `internal/core`, and 80% overall.** Both are smoke detectors, not
targets. A test that asserts nothing raises coverage and catches nothing, and reviewers are
expected to notice the difference. CI enforces both.

`internal/cli` sits lower than the rest on purpose: a command handler's body is a few lines of
wiring around a module call, and the thing worth testing there is the behaviour of the whole
process, which the end-to-end suite covers. What *is* unit-tested in that package is the part with
logic in it: flag parsing, size parsing, and every text renderer.

**New behaviour ships with tests. Bug fixes ship with a test that fails without the fix.** The
second half matters more: a fix without a reproducing test does not prove it fixed anything.

## What gets tested first

When time is short, these get tests before anything else, because they are where a defect costs
the most:

1. Destructive operations: every guard in `clean` and `port free`, especially the refusals.
2. Path resolution and containment: traversal, symlinks, Windows path forms.
3. Redaction: that no secret value appears in any output path, at any verbosity.
4. Exit codes: the full contract table.
5. The stdout/stderr split.

## Running tests

Commands are defined in the `Makefile` and are the same on every platform. `make test` for the
fast unit suite, `make test-all` to include integration and end-to-end, `make bench` for
benchmarks, `make cover` for a coverage report.

Contributors are expected to run the fast suite before pushing and to let CI handle the rest.
